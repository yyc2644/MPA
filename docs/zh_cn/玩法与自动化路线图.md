# 玩法与自动化路线图

本文按公开资料和当前项目状态整理 Pokemon TCG Pocket 的玩法模块，并拆成适合 MaaFramework 渐进实现的自动化任务。

## 公开玩法模块

| 模块 | 游戏入口/概念 | 自动化价值 | 约束 |
| --- | --- | --- | --- |
| 启动已登录游戏 | 标题页、主菜单 | 高 | 用户需提前在模拟器内手动完成登录；脚本只负责启动游戏并进入主页 |
| 免费卡包 | 主页卡包入口 | 高 | 每日免费卡包、扩展包选择、卡包收藏会随新扩展重置 |
| 得卡挑战 | Wonder Pick / 得卡挑战 | 高 | 可选池来自其他玩家开包结果；部分活动有 sneak peek；可能消耗资源 |
| 礼物箱 | Home > Gifts | 高 | 礼物有领取期限；兑换码奖励会进入 Gifts |
| 任务奖励 | Missions | 高 | 每日任务奖励每天只能领一次，且过期不可补领 |
| 商店 | Shop、Limited Time、Events、Premium | 中 | 免费项、活动兑换、高级通行证项分散在不同页签；付费购买不应自动确认 |
| 卡牌收藏 | My Cards、Dex、Flair | 中 | 可用于检测重复卡、语言版本和可交易/可分享候选 |
| 展示 | Binders、Display Boards | 低 | 主要是展示和社交，不是每日收益核心 |
| 机器人对战 | Solo Battle、Step-up/Event Battle | 高 | 适合做任务、活动奖励、快速投降或固定策略刷图 |
| 真人对战 | Versus、Ranked、Private Match | 中 | 排位有赛季限制；掉线约 120 秒内可重连；自动化策略需要避免误操作 |
| 送卡 | Social Hub > Share | 中 | 开始游戏 14 天后解锁；只能给好友；接收方每天只能通过 Share 收一张卡 |
| 交换卡牌 | Social Hub > Trade | 中 | 开始游戏 14 天后解锁；只能和好友交易；同一时间只能进行一个交易；交易有卡牌资格、稀有度和资源限制 |
| 好友与社交 | Social Hub、Friends、Thanks | 中 | Share、Trade、Wonder Pick 都依赖好友关系或社交数据 |
| 礼品码 | 网页兑换 | 低 | 官方说明 gift code 不能在 App 内兑换，需要网页输入 support ID 和 gift code |

## 当前仓库状态

已存在：

- `StartUp`：启动、标题页点击、通知关闭、回主页。
- `Gacha`：抽卡基础流程。
- `BeginnerGuide`：新手/对战入口草稿。

新增骨架：

- `DailyRoutine`：每日流程入口，串联启动、礼物、抽卡、得卡挑战、商店免费项和任务奖励。
- `ClaimGifts`、`WonderPick`、`ShopFree`、`ClaimMissions`。
- `SoloBattle`、`VersusBattle`。
- `ShareCard`、`TradeCard`。

## 实现优先级

### P0：项目可交付基础

- 补齐 `assets/interface.json`，让客户端能看到任务。
- 不提供登录、账号切换、账号绑定或账号密码保存能力；用户需自行完成模拟器内登录。
- 统一资源命名，避免 `Click_index` 这类跨模块通用节点名继续扩散。
- 建立截图样本目录，用固定分辨率、语言、DPI 标注 ROI 来源。
- 多模拟器场景使用独立调度器控制多台已登录模拟器，每个模拟器绑定一个 ADB 地址和一个 Maa tasker。

### P1：每日收益闭环

- 启动后稳定回主页。
- 领取 Gifts。
- 打开免费卡包，并支持按扩展包和卡包封面选择。
- 执行可用 Wonder Pick，默认避免消耗付费资源。
- 领取每日/活动任务奖励。
- 领取商店免费商品和活动免费项。

### P2：对战

- Solo Battle：先做进入、选卡组、开局、自动投降/自动确认奖励。
- PVE 自动对战：再做基础出牌策略，例如可进化则进化、可贴能量则贴、能攻击则攻击。
- Versus：先支持进入、重连、结束确认，不默认自动打排位。

### P3：社交与卡牌流转

- Share：按好友、稀有度、重复数量筛选可送卡。
- Trade：按好友、愿望单、稀有度、语言/闪卡规则筛选候选。
- 自动接受交易前必须二次确认，避免误换稀有卡。

## 风险和边界

- 不自动购买付费道具、金币、通行证。
- 不保存、输入或管理第三方账号密码、验证码。
- 不提供账号切换或账号绑定自动化。
- 不默认进行真人排位自动对战。
- 对交易、送卡、分解/闪卡等不可逆或半不可逆操作，必须有白名单或确认机制。
- 每个功能上线前都需要真实截图回放测试，Maa 的资源加载通过不等于流程可用。

## 多模拟器串行运行

MaaFramework 的 Python API 可以分别创建 `Resource`、`AdbController` 和 `Tasker`。因此 10 个已登录模拟器实例可以由项目调度器依次控制，而不是让一个客户端界面强行同时控制 10 路。

当前推荐模式是串行执行：一个模拟器跑完完整流程后，关闭或释放当前模拟器，再启动下一个模拟器继续跑。这样比 10 路并发更省 CPU、内存和 ADB 带宽，也更容易排查卡住的实例。

已提供 `tools/multi_instance_runner.py`：

```bash
python tools/multi_instance_runner.py --config config/multi_instance.jsonc --task DailyRoutine
```

配置方式：

1. 复制 `config/multi_instance.example.jsonc` 为 `config/multi_instance.jsonc`。
2. 给每个模拟器填写独立的 `adb_path` 和 `address`。
3. 如需自动打开模拟器，给每个实例配置 `start_command` 和 `startup_wait`。
4. 如需跑完自动关闭模拟器，配置 `stop_command`。
5. 每个实例可以单独配置 `task`，例如 `StartUp`、`Gacha`、`DailyRoutine`。

注意事项：

- 默认 `--max-workers 1`，也就是串行执行。只有确认机器性能足够时才建议手动提高并发。
- 每个模拟器必须有稳定且唯一的 ADB 地址。
- 每个模拟器内的登录状态由用户自行维护，脚本只负责登录后的日常流程。
- 后续如果 pipeline 使用 Python Agent 自定义动作，需要再把 agent 注册方式接入多实例 runner。
